# ADR-006: Toolsets select surface; capabilities grant authority; the operator decides both

**Date:** 2026-09-01
**Status:** Active
**Decision method:** AI proposal, human approved — informed by reading GitHub's MCP server.

## Goal

Decide how a deployment chooses which tools exist, given ~700 reachable operations and a tool
surface a model must be able to choose from.

## Context

The in-scope reachable surface is far larger than any usable tool list. The widest server in the
surveyed field ships 51 tools; the core ticket loop is about ten.

GitHub's MCP server solves this with **toolsets** — 21 named groups, selected by the operator at
launch via `GITHUB_TOOLSETS`, with a `default` set and an `all`. Two details are worth copying and
one is worth noting as absent:

- Each toolset carries **its own instructions**, and they **compose based on what else is
  enabled** — a pull-requests instruction gains a paragraph only when the repos toolset is also
  on.
- There is **no runtime enabling.** No `enable_toolset` tool, no dynamic discovery. The operator
  decides before startup.

## Decision

**Two orthogonal dimensions.**

| | Question it answers | Mechanism |
|---|---|---|
| **Toolset** | does this tool *exist* in the surface? | operator config at launch |
| **Capability** | may an existing tool *act*? | fail-closed `PolicyBackend` (ADR-003) |

Toolsets: `context`, `tickets`, `help_center`, `people`, `queues`, `reporting`, `export`, `admin`.
**Default: `context` + `tickets`.** `all` enables everything registered.

**`context` is not optional.** It is always registered regardless of configuration —
`whoami`, `describe_capabilities`, and `describe_ticket_form`. A model that has not called
`describe_ticket_form` is guessing at which fields exist and which are required to solve, and
those vary per form and per account.

**Instructions are per-toolset and compose.** The server's instruction text is assembled from the
enabled toolsets, so a deployment without `reporting` never spends context on aggregation
guidance, and the pagination warnings appear only alongside tools that paginate.

**No runtime enabling.** Nothing lets a model widen its own surface mid-conversation.

## Rationale

**Surface and authority are different questions, and the field conflates them.** Every server
surveyed treats "the tool exists" and "the tool is permitted" as one thing. Separating them means
a deployment can register the `tickets` toolset while granting only `ticket.read` — the tools are
visible and described, and the ones that would write refuse. That is a better failure than a
missing tool, because the model can *see* the capability exists and report what an operator would
have to change.

**Per-toolset instructions are the mechanism our findings need.** This project's research is
mostly of the form "you must know X before calling Y" — close is terminal, `public` inherits,
cursor paging restricts sorting, solving needs fields that vary by form. A single global
instruction block would spend context teaching a model about tools it does not have. Composed
per-toolset, it teaches only what applies.

**Runtime enabling would let the model expand its own surface.** Capabilities would still gate
authority, so the risk is bounded — but surface breadth is an operator decision, and a model that
can turn on `admin` because it decided it needed to has inverted who is in charge. GitHub appears
to have reached the same conclusion; the dynamic mode is the obvious thing to build and their
shipped server does not have it.

**A changing tool list is also a poor client experience.** Clients cache tool lists, present them
in UI, and do not all handle mid-session changes well.

## Rejected alternatives

**One flat surface, everything registered.** Simplest, and wrong at this size: tool-selection
accuracy degrades, and every request pays for descriptions of tools it will never use.

**Runtime enabling via meta-tools** (`list_available_toolsets`, `enable_toolset`). Attractive —
it is genuinely progressive disclosure. Rejected on the authority argument above, and because it
adds a failure mode where the model's view of its own surface and the server's disagree.

**Toolsets *as* capabilities — one dimension.** Tempting, and it is what the field does. Rejected
because it forces a false choice: to grant read-only access to tickets you would have to remove
the write tools from the surface, and then nothing can tell the model those operations exist but
are not permitted.

## Implementation

- Toolset membership is declared in one table, and a test asserts every registered tool belongs to
  exactly one toolset — an unassigned tool must fail loudly rather than silently landing in the
  default set.
- `mcp/_capabilities.py`'s precedent from `csa-google-workspace` applies: the server must not
  advertise a capability no registered tool can exercise. With toolsets that check becomes
  configuration-dependent, so it runs against the *enabled* set.

# ADR-001: Do not implement families this project cannot test

**Date:** 2026-08-31
**Status:** Active
**Decision method:** Human directive — the scope call was made by the project owner;
AI supplied the access audit and recorded the reasoning.

## Goal

Decide what to do about the parts of the Zendesk API that the development account cannot
reach, before any of them get built.

## Context

`scripts/probe_access.py` walked every family in `analysis/operation-inventory.csv` and
classified what the development credential reaches. **748 of 882 operations (85%) are
confirmed reachable.** Forty-seven are refused:

| Family | Ops | Refusal |
|---|---:|---|
| IT Asset Management — assets, types, locations, statuses | 23 | 403 |
| Group SLA Policies | 7 | 403 |
| Workspaces (contextual workspaces) | 7 | 403 |
| Ticket Form Statuses | 4 | 403 |
| Audit Logs | 3 | 403 |
| Help Center Service Catalog Items | 3 | 404 |

A 403 here means **authenticated and refused** — a plan or feature boundary, not a
credential fault and not a defect. These are add-ons and higher-tier features the
development account does not have.

The project's method throughout has been that **a probe beats documentation**: every
behavioural claim in `analysis/` was established by calling the API and looking at what came
back, and doing so has repeatedly contradicted both Zendesk's specs and its prose. Response
shapes, pagination style, error envelopes and required-field semantics have all differed from
what was written down.

## Decision

**These six families are out of scope. No `Backend` methods, no client methods, no MCP tools.**

They remain fully documented — in `analysis/API-SURFACE.md`, in the operation inventory, and
here — as *known and deliberately excluded*, with the evidence for the exclusion.

Two things this decision does **not** do:

1. **It does not exempt the error layer.** Plan boundaries differ per account, so any
   deployment can meet a 403 on an endpoint we did implement. The taxonomy must still
   distinguish *"your plan does not include this"* from *"this is broken"* and from *"your
   credential is wrong"*, everywhere. That work is unaffected.
2. **It does not close the question permanently.** See `WAITING-FOR/WAITING-FOR-001.md`
   for the conditions that would reopen it.

## Rationale

**Untested code is a claim, not a capability.** Everything else here will be built TDD against
a `FakeBackend`, with a gated live suite, following the pattern in the two sibling projects.
For these families there is no live suite possible — so the fake would be authored from a spec
that has already been wrong about pagination in 96 of 96 Help Center GETs, about error envelope
shapes four times over, and about which paths exist at all. The fake would encode our guess, the
tests would confirm our guess, and the suite would go green on fiction.

**The response shapes would be invented.** Structured output means `TypedDict`s built from
observed payloads. With no payload to observe, every field name and type is inferred from a spec
that carries no examples for these families.

**A tool that always fails is worse than an absent one.** It occupies space in the tool list,
consumes context on every request, and offers a model an action it can never complete. The
failure surfaces at the worst moment — mid-task, after a plan has formed around it.

**The cost of exclusion is low and reversible.** Forty-seven operations, 5% of the surface, none
of it in use at the reference account, and none of it load-bearing for the workloads this
project exists to serve. Adding a family later is additive work, and by then it can be built the
way everything else was — against something real.

## Rejected alternatives

**Generate the backend methods anyway and mark them untested.** The generator can emit them
almost for free, which is exactly the trap: near-zero cost to produce, real cost to every reader
thereafter, who must work out which methods have been exercised and which are decoration. It
also puts unverified code behind a public API, where removing it later is a breaking change.

**Implement and let them 403 at runtime.** Shifts the cost onto the user, who discovers the
limitation from a failed call instead of from documentation. It also means shipping code whose
only observed behaviour is failing.

**Find another Zendesk account with the missing plans.** Correct in principle and the right
answer if such an account appears — recorded as the trigger in WAITING-FOR-001 rather than as a
blocker now. Provisioning one to develop 5% of a surface nobody here uses is not proportionate.

**Implement only Audit Logs**, as the one refusal with plausible value for a security
organisation. Same testing objection, three operations, and the value is speculative until
someone has the plan and a use for it. WAITING-FOR-001 covers it.

## Implementation

Not applicable — the decision is to build nothing. Its observable form is an absence, which is
why it is written down.

- `analysis/API-SURFACE.md` §4 records the audit and the refusals.
- `scripts/probe_access.py` reproduces the audit; re-run it if the account's plan changes.

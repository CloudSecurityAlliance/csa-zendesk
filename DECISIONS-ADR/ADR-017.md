# ADR-017: If a surface can authenticate, it must be able to log out

**Date:** 2026-09-19
**Status:** Active
**Decision method:** Human decision, overriding an AI proposal — Block 0e's plan omitted `logout`
from the MCP surface on the AI's reasoning; the project owner rejected that reasoning and supplied
the asymmetry principle and the reversibility-vs-destructiveness distinction that replace it.

## Goal

Decide whether an MCP server that can acquire a credential must also expose a way to relinquish
it — for Block 0e's read-only server specifically, and as a rule for CSA's MCP servers generally.

## Context

Block 0e's plan (`docs/superpowers/plans/2026-09-19-block-0e-read-only-mcp-server.md`, Task 6)
registers `authenticate` and `auth_status` as tools and deliberately left `logout` out of the MCP
surface, on the grounds that it revokes a live 90-day credential server-side and irreversibly, so
it is a destructive write belonging to the capability model ([ADR-010](ADR-010.md)) rather than to
"auth housekeeping." A test, `test_logout_is_deliberately_not_a_tool`, asserted the absence.

That gap is not hypothetical, and it is not unique to this plan. `csa-google-workspace` ships an
`authenticate` tool and no `logout` or `revoke` tool at all — a shipped, in-production server that
has already built exactly this asymmetry once, without anyone flagging it. `csa-zendesk` was about
to build it a second time, deliberately, with a test protecting the omission.

**Checked against the existing ADR set before writing this one, not one at a time:**

- **[ADR-009](ADR-009.md)** (public client, one token file, refresh handling) governs how the
  credential is stored and refreshed. It says nothing about which tools a server exposes over that
  credential, so there is no conflict — but its 2026-09-19 amendment supplies a load-bearing fact
  this decision depends on (see Rationale).
- **[ADR-010](ADR-010.md)** derives capabilities from a classification of Zendesk's 822 in-scope
  Support API operations. Auth-lifecycle operations — logging in, checking status, logging out —
  are not Support API operations and were never in that classification; `analysis/operation-classification.csv`
  has no row for them. Block 0e's own Task 6 already treats `authenticate` and `auth_status` as
  sitting outside `policy._GATES` for this reason (`test_no_registered_tool_maps_to_a_write_operation`
  explicitly skips them). This ADR does not contradict ADR-010's model; it extends the exemption
  ADR-010's own capability gate already leaves in place for auth-lifecycle tools to the third member
  of that set, `logout`, and says explicitly that the gate is scoped to the classified operations,
  not to everything the server can do.
- **[ADR-015](ADR-015.md)** (OAuth only, no further tokens minted) is unaffected: `logout` revokes,
  it does not mint.
- **[ADR-016](ADR-016.md)** (tools are atomic and bucket-pure) is satisfied by construction —
  `logout` does one thing.
- **[ADR-003](ADR-003.md)**, since narrowed by ADR-010, is the source of the reversibility framing
  the plan borrowed and then misapplied to a case it wasn't built for. See Rationale.

None of the four existing ADRs answers this question differently; the plan's own prose, not an
ADR, is what this decision overrules.

## Decision

**If a CSA MCP server exposes a tool to acquire a credential, it must expose a tool to relinquish
it, reachable at least as easily as the tool that acquires it.** Concretely, for `csa-zendesk`:
`logout` becomes a third tool in Block 0e's server, registered and reachable at the same rung as
`authenticate` and `auth_status` — not gated behind a capability that the read-only rung does not
grant, and not deferred to the CLI when an MCP surface already exists.

This is stated as a general rule for CSA's MCP servers, not a `csa-zendesk` special case:
**an interface that can say "get more access" must be able to say "give it up," and the second
must not be harder to reach than the first.**

## Rationale

**The asymmetry runs the wrong way.** An interface that can acquire a credential but not relinquish
it makes the easy path "get more access" and the hard path "give it up." The safety valve has to be
at least as reachable as the thing it protects against, or it isn't a safety valve — it's a decision
made once, at login, that the interface then has no way to revisit.

**Destructiveness and reversibility are different axes, and this project already knows that.**
DEC-015 (`CINO-Platform-Engineering`'s cross-project decision log) classifies an operation on
four independent axes — Effect, Reversibility, Reach, Authority —
precisely because MCP's own annotation vocabulary (`readOnlyHint`/`destructiveHint`/`idempotentHint`)
*conflates* the first two, which is the exact failure DEC-015 was written about
(`csa-skilljar`'s T16 finding: `send_password_reset` marked `destructive_hint=True` when what it
does is contact a third party, not destroy anything). The plan's reasoning made the same
conflation in the opposite direction: it called `logout` "destructive" — true, in the MCP-hint
sense that it changes state and cannot be replayed against the same token — and treated that label
as sufficient grounds for exclusion, without separately asking DEC-015's actual Reversibility
question: *can it be undone, and for how long?*

Asked that question, `logout` does not sit with [ADR-010](ADR-010.md)'s twenty genuinely
irreversible-or-permanent operations (ticket purge, user purge, identity merge). Those cost
something no command reverses — another person's data, or a merged identity. `logout`'s cost is
**running `auth login` again.** That is not a hedge: revocation was confirmed on 2026-09-19,
against the live tenant, to invalidate **both** the access token and its paired refresh token
(ADR-009's 2026-09-19 amendment) — logout is complete, not partial, and its recovery path is a
single command available to the same caller who just ran it, with no dependency on anyone else.
A destructive-but-instantly-and-cheaply-recoverable action does not belong in the same tier as a
destructive-and-permanent one, even though MCP's flat `destructiveHint` renders them identically.

**The fleet has already paid for not asking this question once.** `csa-google-workspace` shipping
`authenticate` with no way back is evidence, not speculation, that this gap is easy to build and
easy to miss — it takes noticing that acquisition and relinquishment are a pair, not two
independent features to remember separately.

## Rejected alternatives

**CLI-only logout — what the plan said and what the fleet does today.** Cheapest to write, and
consistent with treating revocation as an out-of-band administrative act. Rejected because it makes
the safety action the inconvenient one: the same session that can authenticate in one tool call has
to leave the MCP client, find the right directory and virtualenv, and run a CLI command to undo it.
An asymmetry that costs nothing to build is still an asymmetry.

**Gate `logout` behind a write capability, so a read-only profile cannot reach it.** Tempting
because it would make `logout` consistent with how every other state-changing operation in this
project is gated ([ADR-010](ADR-010.md)). Rejected because it makes the credential
un-relinquishable at exactly the rung — E1, read-only, `READ=*` — where a user is most likely to be
experimenting with the server and most likely to want out. Gating the exit behind the same
authority ladder as the actions it exists to escape from means only operators who already hold
elevated capability could log out, which inverts the point: the people who most need a cheap way to
stop are the ones running the smallest, most cautious profile.

**A confirmation step before `logout` executes (e.g., a second call to confirm intent).**
Considered as a middle ground — it would reduce the chance of an accidental invocation without
gating the tool away entirely. Rejected: it reintroduces friction on the safety valve, which is the
exact asymmetry this decision corrects, in exchange for protection against a mistake that already
costs one `auth login` to fix. Adding ceremony to prevent a trivially-recoverable error trades a
cheap, self-service risk for a certain cost paid on every legitimate use.

## Affects

- `docs/superpowers/plans/2026-09-19-block-0e-read-only-mcp-server.md` — Task 6's tool set, its
  tests, its self-review, and the README install instructions drafted in Task 7.
- The eventual capability model — a scope note, not a change: [ADR-010](ADR-010.md)'s gates cover
  the classified Support API operations, and auth-lifecycle tools (`authenticate`, `auth_status`,
  `logout`) sit outside that classification by design, reachable at every rung.
- Any future CSA MCP server that ships an `authenticate` tool, including a revisit of
  `csa-google-workspace`, which is named here as evidence and is not otherwise touched by this
  decision.

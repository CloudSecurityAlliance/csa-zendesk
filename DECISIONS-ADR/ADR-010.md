# ADR-010: Capabilities are derived from a classification of every operation, not from one workflow

**Date:** 2026-09-08
**Status:** Active · **Amends** [ADR-003](ADR-003.md)
**Decision method:** Human decision, AI informed — the gap was the project owner's question; the
classification and the proposed model are the answer to it.

## Goal

Give every in-scope operation a capability, derived from what the operation actually does rather
than from the workflow we happened to design first.

## Context

[ADR-003](ADR-003.md) built a ladder ordered by reversibility. It is correct **for tickets**,
because it was derived from the ticket workflow. The rest of the surface was then generalised by
eye, and that generalisation was wrong in three ways.

`scripts/classify_operations.py` classifies all **822** in-scope operations by domain, action,
blast radius and recoverability (`analysis/operation-classification.csv`):

| domain | read | write | delete | config | bulk |
|---|---:|---:|---:|---:|---:|
| ticket | 144 | 99 | 36 | — | 16 |
| people | 74 | 43 | 19 | — | 14 |
| help centre | 96 | 61 | 25 | 16 | 2 |
| admin | 115 | 77 | 33 | 225 | — |

| recoverability | count |
|---|---:|
| n/a (reads) | 425 |
| reversible | 269 |
| recoverable with effort | 108 |
| **irreversible** | **13** |
| **irreversible, permanent** | **7** |

Three findings:

**1. There was no delete capability at all.** 113 delete operations, every one of which the
previous model put behind the same gate as editing a field. `csa-skilljar` split
`content.delete` from `content.write` precisely because *an authoring credential that can create
and update content should not thereby be able to destroy it*, and that was not carried over.

**2. `admin.write` was one flat gate over 225 configuration operations — 27% of the surface.**
Editing a trigger changes the behaviour of every future ticket, silently. By blast radius that
exceeds closing a single ticket, yet `ticket.close` had its own gate granted by no profile while
trigger-editing shared one bucket with listing ticket fields. The previous model gave the sharpest
gate to the scariest-*feeling* action rather than the widest-*reaching* one.

**3. A permanence tier was missing, and two irreversible operations were unnoticed.** Zendesk
soft-deletes first and then offers `DELETE /deleted_tickets/{id}` — *"Delete Ticket Permanently"* —
and `DELETE /deleted_users/{id}`. And `PUT /users/{id}/merge` and
`POST /organizations/{id}/merge` are irreversible identity operations that were never considered,
because ADR-003 reasoned about *ticket* merge only.

**Only 20 operations of 822 are genuinely irreversible.** That precision is the point: it means
the sharpest gates can be very narrow.

## Decision

**Capabilities are `<domain>.<tier>`, plus one cross-cutting axis.**

| Domain | Tiers |
|---|---|
| `ticket` | `read` · `note` · `write` · `reply` · `solve` · `close` · `delete` · `purge` |
| `people` | `read` · `write` · `suspend` · `merge` · `delete` · `purge` |
| `hc` | `read` · `write` · `delete` |
| `admin` | `read` · `write` · `delete` |
| `reporting` | `read` · `export` |
| `raw` | `read` · `write` |

**Cross-cutting: `bulk`.** Required **in addition** to the domain capability for any `_many`,
`/bulk` or `/import` operation. Granting the power to delete one ticket does not grant the power
to delete a thousand.

**Default profile** — everything reversible, nothing outward-facing:
`ticket.read`, `ticket.note`, `ticket.write`, `hc.read`, `people.read`, `reporting.read`,
`admin.read`.

**Granted by no profile:** every `.purge`, `ticket.close`, `people.merge`, `raw.read`,
`raw.write`.

**Re-gated from ADR-003 / the design spec:**

- `mark_ticket_as_spam` moves from `ticket.write` to **`people.suspend`**. Its full name is
  *"Mark Ticket as Spam and Suspend Requester"* — it suspends a user account, and it was in the
  default profile.
- `merge_tickets` stays at `ticket.close` (ADR-004 established merging closes the source).
- `admin.write` carries an explicit blast-radius statement in every tool description that uses it:
  *this changes behaviour for all future tickets.*

> **Correction (2026-09-18):** `merge_tickets` no longer stays at `ticket.close`. A fix wave (Block
> 0c, Task 6's final review) found that `POST /tickets/{ticket_id}/merge` accepts
> `source_comment_is_public` and `target_comment_is_public` — the same mechanism a public reply
> uses to email a requester. That means a merge call can carry **reach**, which `close_ticket` never
> does. `src/csa_zendesk/policy.py` carries an invariant tying the two together: every tool with
> `reach=True` must have a capability in `REACH_CAPABILITIES`, and no profile may grant a
> `REACH_CAPABILITIES` member. Once that invariant existed, `merge_tickets` sharing `ticket.close`
> with the non-reaching `close_ticket` was no longer satisfiable — one gate cannot correctly express
> both "reaches a person" and "does not." The fix gave `merge_tickets` its own capability,
> `ticket.merge`, added to `REACH_CAPABILITIES` alongside `ticket.reply`. This ADR's decision that
> merging closes the source (ADR-004) is unaffected — `ticket.merge` is still positioned as a close,
> not a write — only the *sharing* of `ticket.close` with `close_ticket` is corrected.
>
> The "granted by no profile" list above (`ticket.close`, `people.merge`, `raw.read`, `raw.write`,
> every `.purge`) is likewise incomplete as written: `ticket.merge` is granted by no profile too
> (`src/csa_zendesk/policy.py`'s `PROFILES["full"]` excludes it explicitly, alongside `ticket.reply`,
> `ticket.close` and `raw.*`). See `analysis/TOOL-BOUNDARIES.md` and
> `analysis/tool-boundaries.csv` for the corrected tool table.

## Rationale

**Deriving from the data caught what deriving from a workflow could not.** The three findings were
all invisible from the ticket workflow, and all obvious from a table. This is the same lesson as
ADR-004's observational testing: measure the system rather than reason about it.

**`bulk` as an additive axis is better than a bulk tier per domain.** It is one capability instead
of six, it composes with any future domain, and it expresses the real distinction — magnitude is
orthogonal to authority. A caller with `ticket.delete` and no `bulk` can delete a ticket it has
identified, which is usually what was wanted.

**Splitting `delete` from `write` costs nothing and closes a real hole.** A deployment that lets an
agent triage tickets has no reason to let it delete them, and the previous model could not express
that.

**Permanence deserves its own tier because Zendesk models it that way.** Soft delete is
recoverable-with-effort; `deleted_tickets` deletion is not. Using the platform's own two-step
structure means the capability boundary sits where the platform's does.

**20 irreversible operations means the strictest gates are cheap.** There was a temptation to keep
the model coarse for simplicity. The classification shows the strict tier is tiny, so precision
costs almost nothing in configuration burden.

## Rejected alternatives

**Keep the coarse model and rely on tool descriptions.** What the field does — no server surveyed
gates its own tools at all. Rejected: a description is advice, a gate is a control.

**A `delete` tier per domain plus a `bulk_delete` tier per domain.** Twelve capabilities where
seven suffice, and it makes bulk-ness look like a property of deleting rather than of any
operation.

**One `destructive` capability covering everything irreversible.** Twenty operations spanning
tickets, users and organizations. Rejected because it forces an operator granting ticket purging
to also grant user merging, which are unrelated authorities.

**Split `admin.write` per object type** — `admin.triggers.write`, `admin.macros.write`, and so on.
Genuinely tempting given 225 operations. Deferred rather than rejected: it multiplies configuration
for a surface that is entirely off by default in 1.0, and the blast-radius warning addresses the
immediate risk. Recorded in `TODO.md` for revisiting if `admin` is ever granted routinely.

## Implementation

- `analysis/operation-classification.csv` is the input to `policy._GATES`, and a test asserts every
  in-scope operation the `Backend` exposes has a gate consistent with its classification.
- The fail-closed property is unchanged: an undeclared method is refused.
- `bulk` is checked *in addition to*, never instead of, the domain capability — asserted by a test
  that a `destroy_many` call with `ticket.delete` but no `bulk` is refused.

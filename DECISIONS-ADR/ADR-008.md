# ADR-008: A generic request tool exists, refuses what curated tools cover, and names its own remedy

**Date:** 2026-09-01
**Status:** Active
**Decision method:** Human decision, AI informed — the requirement and its framing ("attempt
unusual things, then request access") were the project owner's.

## Goal

Decide whether the server exposes a generic request tool, and if so how it avoids becoming a
bypass of everything the curated surface exists to guarantee.

## Context

The curated tool surface (ADR-006) covers the actions the web interface offers. The reachable
API is roughly 700 operations. Everything not curated is unreachable through MCP — which is
correct for the common case and wrong for the unusual one: a legitimate task nobody anticipated
has no route at all, and the answer *"that is not possible"* is false.

One surveyed server ships a generic passthrough. It also discards structured output, tool
annotations and every per-tool warning — which is why this ADR is about constraint rather than
about whether to build it.

## Decision

**Two tools, not one:**

- **`zendesk_read(path, params)`** — GET only. `read_only_hint: true`.
- **`zendesk_request(method, path, params, body)`** — any verb. `destructive_hint: true`.

Both are **off by default**, gated by `raw.read` and `raw.write`, which no default profile grants.

**Both refuse any path a curated tool already covers**, and say which tool to use instead.

**Every refusal names its own remedy** — the missing capability, and what an operator would
change to grant it.

## Rationale

**Annotations are per-tool, so the split is forced.** The same argument as ADR-003: one tool that
can both read a ticket and delete an organization must be annotated for the worst case, and a
client that sees `destructive_hint: true` on the tool used for exploration learns to ignore the
hint.

**Refusing covered paths is what stops it being a bypass.** This is the load-bearing constraint.
Without it, a model faced with forty specific tools and one flexible tool will reach for the
flexible one — it requires less selection reasoning — and in doing so it routes around every
warning we spent this design writing: that closing is terminal, that `comment.public` inherits
from the ticket, that cursor paging silently discards `sort_by`, that solving needs fields which
vary per form. The escape hatch is for surface we **do not cover**, not an alternative route to
surface we do.

The check is mechanical: `analysis/operation-inventory.csv` already maps every operation, and the
tool registry knows which are curated. A refusal reads *"`PUT /api/v2/tickets/{id}` is covered by
`update_ticket`, which enforces required-field checks and comment visibility. Use that."* As
curated coverage grows, the hatch automatically narrows — the constraint maintains itself.

**Refusal-with-a-remedy is the workflow, not an error path.** The requirement was that the model
should *attempt* unusual things and *request access if need be*. That makes the refusal the
product: it must name the capability, name the setting, and be quotable to a human who can decide.
This is ADR-006's argument one level out — a visible tool that refuses informatively beats an
absent one, because the model can report what would have to change instead of concluding the
platform cannot do it.

**It converts an unknown unknown into a request.** Today, an uncovered operation is invisible: the
model does not know it exists, so nobody learns the gap is there. With the hatch, an attempt
produces either an answer or a specific, logged request — which is also how we find out which
uncurated operations people actually need.

## What it does not get to skip

- **Injection wrapping.** Raw responses contain ticket bodies. Content passes through the same
  wrapping as every other read; the hatch is an exception to curation, not to safety.
- **The pagination invariant.** It must still refuse to emit both pagination styles on one
  request (`API-SURFACE.md` §5.4b), because that failure is silent and returns a 200.
- **Rate limiting and retries**, including the per-endpoint buckets.
- **Error taxonomy.** Responses go through the same parser, so a `403` is still reported as a plan
  boundary rather than an outage.

## Rejected alternatives

**No escape hatch.** The position I argued for previously. It makes "100% of the API" false for
MCP users, and leaves genuinely reasonable requests with no route and no explanation.

**One tool for all verbs.** Cannot carry two honest annotations.

**Allow it to cover curated paths.** Simpler, and it makes the hatch the path of least resistance
for a model — which silently discards the safety semantics that the curated tools carry.

**On by default, read-only.** Tempting, since GET is harmless. Rejected because "harmless" is
wrong for reads here: an unrestricted GET can pull audit logs, every user record, and the full
text of any ticket, bypassing whatever the operator thought they were scoping with toolsets.

**A path allowlist configured by the operator.** More precise, and it makes the operator maintain
a list of API paths — which nobody will keep current. The covered-path refusal achieves the same
protection from data we already hold.

## Implementation

- The covered-path check keys on `(method, path template)`, resolved from the inventory, so an
  interpolated `/api/v2/tickets/123` matches the curated `/api/v2/tickets/{id}`.
- A test asserts that every curated tool's operation is refused by the hatch — the two must not
  drift apart as tools are added.
- Refusals are logged with the attempted method and path (never the body), so the uncurated
  operations people actually reach for become visible and can inform later curation.
- The tool descriptions state plainly that a specific tool should be preferred where one exists,
  and that these exist for operations the server does not model.

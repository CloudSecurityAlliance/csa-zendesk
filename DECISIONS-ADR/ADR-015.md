# ADR-015: OAuth only — API token support is removed, and no further tokens are minted

**Date:** 2026-09-17
**Status:** Active
**Supersedes:** the *"API token support ships, deprecated"* clause of [ADR-009](ADR-009.md). The rest
of ADR-009 — public client, PKCE, one token file, refresh behaviour — stands unchanged.
**Decision method:** Human decision, after an AI review surfaced the deadline.

## Goal

Decide what the shipped server does about Zendesk API tokens, given that the window to create one
closes in 40 days.

## Context

[ADR-009](ADR-009.md) recorded two vendor deadlines and then, separately, chose to ship API token
support as a deprecated path:

| Date | What happens |
|---|---|
| **2026-10-27** | No account can create a new API token. Existing tokens keep working |
| **2027-04-30** | Existing API tokens stop working |

Both dates lived only in that ADR's prose and were tracked nowhere
([WAITING-FOR-003](../WAITING-FOR/WAITING-FOR-003.md) now carries them). The obvious mitigation —
mint every token the project could ever want before 2026-10-27, while that is still possible — was
considered and **declined**.

The project also already held the opposite position elsewhere. `GOALS.md` states that **"nothing is
callable against a real Zendesk until"** Block 0b lands. Token support was an exception to a rule the
project had already written down for itself.

## Decision

**The shipped server authenticates by OAuth and by nothing else.**

1. **No API token code path.** `CINO_CSA_ZENDESK` and `CINO_CSA_ZENDESK_EMAIL` are not read by the
   server, not as a fallback and not with a warning. There is one way to authenticate.
2. **No further tokens are minted**, including spares, test-context tokens and CI tokens. The window
   closing on 2026-10-27 is allowed to close.
3. **Block 0b is the critical path, with a hard deadline of 2027-04-30.** Not "next" — the only route
   to a live call, and one with a date on it.
4. **Nothing is exempt, including the research scripts.** `scripts/` moves to OAuth with everything
   else. See the amendment below — an earlier version of this decision exempted them.

## Rationale

**A stockpile defers the work that has to happen anyway.** Tokens minted now would buy until
2027-04-30 regardless, and every one of them would be an argument for not building OAuth this quarter.
The deadline is more useful as a forcing function than as something to be insured against.

**One auth path is a materially simpler thing to reason about.** A fallback that silently activates
when OAuth is misconfigured is the shape that makes an auth failure look like a permissions failure —
which ADR-009 was already careful to avoid in its refresh handling. Removing the fallback removes the
ambiguity rather than documenting it.

**The exception contradicted the project's own stated position.** Carrying both "nothing is callable
until 0b" and "tokens continue to work" required a reader to know which one was operative.

## What this costs, named rather than discovered later

**It converts a deadline into a single point of failure with a 40-day fuse.** After 2026-10-27 the
one existing token is irreplaceable. If it is lost, rotated, or revoked before Block 0b ships, the
research scripts stop working and there is no way to re-probe the account until OAuth exists.

That is accepted. The mitigation is not a spare token; it is **Block 0b shipping**, which is the thing
the decision is meant to force.

## Rejected alternatives

**Mint spares before 2026-10-27 and keep the deprecated path.** The obvious move, and rejected on
purpose: it buys nothing that OAuth does not buy permanently, and it converts a hard deadline into a
soft one at exactly the moment a hard deadline is useful. Not wrong in general — a project with no
route to OAuth should absolutely stockpile — but unwarranted here, because the route exists and is
already specified.

**Keep token support with no new tokens.** Half the cost for none of the benefit: the code path, the
fallback ambiguity and the second way to be configured all remain, in service of a credential that
expires on a known date.

**Remove token support from the research scripts too, now.** Originally rejected as stopping the
project dead — and that reasoning was sound about *timing* and wrong about *destination*. See the
amendment: the scripts do move, they just cannot move before there is somewhere to move to.

## Affects

- [ADR-009](ADR-009.md) — its token clause only
- `GOALS.md` near-term — Block 0b's description gains a date
- [WAITING-FOR-003](../WAITING-FOR/WAITING-FOR-003.md) — trigger changes from "mint tokens" to
  "ship Block 0b"
- `README.md`, `CLAUDE.md` — remove token configuration as a supported path
- `docs/superpowers/specs/2026-09-17-csa-zendesk-whole-project-design.md` — B0b is the critical path

## Amendment (2026-09-17): the scripts are not exempt either

**Test the way we plan to use it.** The exemption above kept `scripts/` on API-token auth
indefinitely, which meant the only code exercising a live Zendesk would have been the code using the
credential model we had just deleted. Every probe would have validated a path the product does not
take, and OAuth would have reached production having never run against anything.

**So `scripts/` moves to OAuth with everything else, and becomes its first consumer.** That ordering
is deliberate rather than merely tidy: the probes are read-only, low-stakes and run by hand, which
makes them the right place for an auth flow to fail the first few times. If OAuth works for
`probe_families.py` it works for the library, and we will know that before any tool depends on it.

**What this does not change is the sequence.** OAuth has to exist before anything can be ported to
it, so the order is:

1. **Consolidate.** There are three auth implementations in `scripts/` today — `zd.py` has one, and
   `ui_actions.py` and `probe_families.py` each reimplement it rather than calling `zd.call`. Fold
   them onto `zd.py`'s single chokepoint. This needs no OAuth and turns the eventual swap into a
   one-function change.
2. **Build Block 0b** — the public client, PKCE, the token file, refresh. Unchanged, except that it
   now blocks the research scripts as well as the library, which makes it the immediate next work
   rather than merely the next block.
3. **Strip the token.** `CINO_CSA_ZENDESK` and `CINO_CSA_ZENDESK_EMAIL` stop being read anywhere,
   and `./.env` stops being a credential source.

**The cost is unchanged and still accepted.** Between now and step 2, the scripts keep using the
existing token, because the alternative is that `API-SURFACE.md` cannot be refreshed at all. After
2026-10-27 that token is irreplaceable. Losing it delays research and breaks nothing at runtime, and
the mitigation remains Block 0b shipping rather than a spare credential.

# ADR-007: Surface Zendesk's async jobs; do not invent our own

**Date:** 2026-09-01
**Status:** Active
**Decision method:** AI proposal, human approved.

## Goal

Decide how long-running work is handled, now that two separate sources of it exist.

## Context

Two things in this design take longer than a tool call should, and they are **not the same
problem**:

1. **Zendesk's own asynchronous jobs.** Bulk writes (`update_many`, `create_many`,
   `destroy_many`) do not return a result — they return a **job id**. The outcome, including
   per-record partial failure, is retrieved later from `/api/v2/job_statuses/{id}`. Up to 30 jobs
   may be queued or running before the account is refused with `TooManyJobs`.
   **No server in the surveyed field models this**, and the one official client that models the
   resource does so as a bare fetch with no polling and no completion semantics.

2. **Our own aggregation.** ADR-005's `summarise_*` streams pages and folds them. A six-figure
   corpus is roughly 1,500 requests — minutes under the account limit, hours via incremental
   export.

The first is durable state held by Zendesk. The second is a loop inside our process.

## Decision

**Surface Zendesk's async; bound our own. Hold no job state ourselves.**

**For Zendesk's jobs:** a bulk tool submits the work, then **polls briefly** — a few seconds,
bounded — so that short jobs complete inline and the caller gets the outcome. If the job has not
finished, the tool returns the **job id and its current status**, and `get_job_status` retrieves
it later. The result always reports **per-record outcomes**, never a single success flag: a job
that half-succeeded must not read as success.

**For our aggregation:** no handles. It is **bounded work that reports its own limits**, per
ADR-005 — scope is mandatory, an unbounded request is refused, and the result states how much was
sampled. If the bound is reached, the answer says so and is not presented as complete.

**We hold no job registry, no queue, no background workers, and no state between calls.**

## Rationale

**Zendesk's job state is already durable, and ours would not be.** Their job survives our process
restarting, the MCP client reconnecting, and the machine sleeping. A job handle we invented would
be a key into memory that a local stdio server loses on every restart — and persisting it to disk
is exactly what ADR-005 declined to do for response data. So there is nothing to gain by wrapping
their durable handle in a fragile one.

**Brief polling is where the ergonomics are.** Most bulk operations of the size a conversation
produces finish in seconds. Polling briefly means the common case returns an answer rather than a
receipt, while the long case degrades to a handle instead of a timeout. Blocking indefinitely
would make a tool call an unbounded wait; returning immediately would make every bulk operation a
two-step dance even when it took 400ms.

**Partial failure is the whole point of job statuses.** Zendesk reports per-record results because
bulk operations routinely half-succeed. A tool that flattens that into "done" is the same defect as
one that reports a search `count` it cannot page to: technically a response, and misleading.
csa-skilljar hit this shape already and its batch parser **checks** that succeeded + failed equals
the total rather than trusting it.

**Bounding our own work is simpler and more honest than deferring it.** A `summarise_*` that
refuses an unbounded scope forces the caller to ask an answerable question. A handle would let it
ask an unanswerable one and then discover that hours later.

**The 30-job ceiling is a real constraint.** `TooManyJobs` is an account-wide limit, so a tool
that fires jobs freely can break unrelated integrations. That argues for submitting fewer, larger
jobs rather than many small ones, and for surfacing the ceiling in the error rather than retrying
into it.

## Rejected alternatives

**Block until the job completes.** Simple, and it makes a tool call an unbounded wait — the worst
citizen in an interactive session.

**Return the job id immediately, never poll.** Honest and mechanically simplest. Rejected because
it makes every bulk operation two round trips even when the work took under a second, and models
handle "submit then poll" poorly — they tend to report the submission as the outcome.

**Our own job handles for long aggregations.** Would need a registry, a lifetime, cleanup, and
state that survives restarts — which means persistence, which ADR-005 declined. Bounding the work
achieves the same user-visible outcome with none of it.

**Background workers or a task queue.** Wrong shape entirely for a local stdio server launched by
an MCP client.

## Implementation

- `get_job_status` lives in whichever toolset owns the bulk operation, not in a toolset of its own.
- The polling budget is configurable with a small default, and is never unbounded.
- A test asserts a partially-failed job is reported as partial, not as success — the failure this
  is most likely to regress into.
- `TooManyJobs` gets its own typed error naming the account-wide ceiling, so it is not mistaken for
  a rate limit or for a fault in the caller's own request.

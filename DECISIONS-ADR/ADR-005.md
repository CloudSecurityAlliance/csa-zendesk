# ADR-005: Aggregate in memory for the model; export to disk for people; persist neither

**Date:** 2026-09-01
**Status:** Active
**Decision method:** Collaborative — three shapes were put up with a recommendation; the project
owner chose the split.

## Goal

Decide how bulk reads work, given that the workload motivating this project is analytical and the
volumes involved cannot fit in a model's context.

## Context

The questions this tool exists to answer are aggregate ones — queue health, response-time
distributions, which records have passed a verification date. The obstacles:

- **Search caps at 1000 results** while reporting a count orders of magnitude larger
  (`API-SURFACE.md` §5.2).
- **Incremental export** is the only uncapped path and runs at **10 requests per minute**.
- A model's context holds a few hundred tickets before it is useless for anything else.

One surveyed server solves this by writing responses to disk and exposing a query tool over the
files, with named queries per response type. It is the most direct answer anyone in the field has.

## Decision

**Two mechanisms, and no persistence in either.**

**Aggregate in memory, for the model.** `summarise_*` tools stream pages, aggregate as they go,
and discard each page. Rows never reach the model and never touch disk. The result is a small
table — a distribution, a grouped count, a set of percentiles.

**Export to disk, for people.** `export_*` tools write a file for a human or a separate analysis
tool, to an operator-configured directory. The model receives a summary and a path. **The model
does not query the file**; there is no query tool over exports.

**Nothing is cached.** `SECURITY.md`'s position stands unamended: no response persistence, no
attachment cache, no token file.

Two constraints the aggregation tools carry:

- **Scope is mandatory.** A `summarise_*` call takes a view, a date range or a query, and
  **refuses an unbounded request** rather than silently running for an hour. It reports how much
  it actually sampled, so a truncated answer is never presented as a complete one.
- **Long calls need a story.** A six-figure corpus is roughly 1,500 requests — minutes under the
  account limit, hours via incremental export. Either the work is capped and says so, or it
  returns a job handle. That reconnects with the async question in `TODO.md` B4 and is not
  settled here.

## Rationale

**Store-and-query reverses a stated security position, and the others do not.** `SECURITY.md`
says nothing is persisted by design; both sibling projects say the same, and one records that
proposing persistence *changes the security posture and needs its own ADR*. What would be
persisted here is not configuration — it is **ticket bodies**: customer correspondence, and on
this account, incident-response and quality-management audit evidence. Writing that to disk so a
model can grep it is a materially different product.

**Nobody wants ten thousand tickets; they want the distribution.** The aggregate *is* the answer.
Returning rows so that something else can aggregate them is a detour through the most expensive
resource in the system.

**Store-and-query assumes a filesystem the client may not have.** In a harness with file tools the
model could read the file directly and our query tool is redundant. In a plain MCP client there
are no file tools, so the file is reachable only through us — meaning we would build a query
language *and* teach the model our response shapes, purely to work around context limits.

**The export path is the workflow that already exists.** The March 2026 analysis of this account
was built from CSV exports, cross-referenced outside any tool. That is evidence exports belong to
people, and that the model's job is to answer questions rather than to hold data.

**Aggregation keeps content away from the model.** A summarising tool that never emits row text
is also the strongest available mitigation for prompt injection on the bulk path — untrusted
ticket bodies are counted, not read aloud.

## Rejected alternatives

**Store and query.** The most capable option and the one with a working precedent. Rejected on the
persistence reversal above, and because its benefit is covered twice over — by aggregation for
models and by export for people.

**Return raw pages and let the model aggregate.** What every server in the field does. It is why
none of them can answer an analytical question.

**Only export, no aggregation.** Would leave the model unable to answer anything about volume
without a human in the loop, which is most of the motivating workload.

## Implementation

- `summarise_*` tools live behind a `reporting.read` capability; `export_*` behind a separate
  `reporting.export`, **off by default**, with the destination directory operator-configured and
  never defaulted to the working directory.
- Aggregation must not retain rows after a page is folded in — asserted by a test, not by care.
- Whether `export_*` ships in 1.0 or waits until the read path is proven is **not decided here**.

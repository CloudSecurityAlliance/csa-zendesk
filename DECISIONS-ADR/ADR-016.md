# ADR-016: Tools are atomic and bucket-pure; workflow lives in plugins

**Date:** 2026-09-17
**Status:** Active
**Decision method:** Collaborative — an experiment falsified the prior assumption, and the human decided the replacement.

## Goal

Decide what a tool *is*, given that Zendesk models five different impact levels as one `PUT`.

## Context

The whole-project design ([2026-09-17](../docs/superpowers/specs/2026-09-17-csa-zendesk-whole-project-design.md) §4)
established that **a tool never spans two impact buckets**, and then assumed tools would be built by
*grouping* operations — "within a bucket, group by task and argument shape."

A validation slice was scoped to test that before building 335 operations' worth of it. The test
failed immediately, from two table lookups and no code.

`PUT /api/v2/tickets/{ticket_id}` is classified in `analysis/operation-classification.csv` as:

```
domain=ticket  action=write  radius=record  recoverability=reversible  reach=—
```

That one operation is how you do **all** of these:

| Body | Effect | Reversibility | Reach |
|---|---|---|---|
| fields, assignee, tags | write | reversible | internal |
| `comment.public = false` | note | reversible | internal |
| **`comment.public = true`** | **reply** | **irreversible** | **contacts-a-person** |
| `status = solved` | solve | on-ramp to terminal | internal |
| `status = closed` | close | terminal immediately | internal |

So the table calls *reversible and internal* the operation that emails a customer and cannot be
unsent — under-reporting danger on the single most consequential call in the project. And there is
**no ticket-comment-create operation anywhere** in the 822: every comment-creating path in the
inventory belongs to Help Center or Community. Two operations carry `reach=yes` with a write, and
neither is the public reply.

This is not a gap in the table. It is a category error: **the table's unit is the operation, and the
design's unit is the call.** No amount of correcting rows repairs it, because the row does not exist
and cannot.

Both prior decisions had reached the edge of this without generalising it. ADR-003 concluded that
"public replies are their own tool rather than a flag on a comment" — for one case. DEC-015 records
that "reach may be a property of the call rather than the tool."

## Decision

**A tool is `(operation × constrained arguments)`.** One operation may back several tools, each
narrower than it, and **the constraint on the request body is what makes the tool bucket-pure.**

```
update_ticket        PUT /tickets/{id}   refuses `comment` and `status` in the body
add_internal_note    PUT /tickets/{id}   comment only, public forced false
reply_publicly       PUT /tickets/{id}   comment only, public forced true      <- reach
solve_ticket         PUT /tickets/{id}   status only, solved
```

**Tools are atomic. There are no composite tools**, even though Zendesk's own `PUT` is a natural
composite and `policy.py`'s `Gate` type already supports a capability set computed from the call's
arguments.

**Workflow lives in plugins, not in the server.** The sequencing a real ticket needs — assign to
self, then reply, then note; or on close, log time and add a closing note — is tenant opinion. The
repository ships one simple example plugin; CSA's own procedures live in separate plugins, and a
different Zendesk customer writes their own.

**The line:** the server states what is *true*; a plugin states what to *do*. "Close is terminal",
"`comment.public` inherits from the ticket's first comment", "this form requires these fields", "a
public reply cannot be unsent" are facts about Zendesk, identical for every tenant, and they belong
in tool descriptions and ADR-006's composing instructions. "We assign to ourselves first" is opinion.

## Rationale

**The server cannot know the tenant's configuration, and does not need to.** Required fields vary
per `ticket_form_id`, conditional rules make the requirements model over-report
(TODO **C1**), and the API **refuses a bad solve with a 422 that names what is missing** — probed
directly on 2026-08-30, and the reason the web UI's red-text behaviour is reachable from code. The
server surfaces the refusal; the agent reacts; the plugin advises. Modelling the tenant would be
both impossible and unnecessary.

**Authority beats atomicity.** An operator must be able to grant "assign tickets" without granting
"email customers". If those are one tool, they cannot. That argument holds regardless of how natural
the composite is.

**`GOALS.md` promises "any Zendesk customer gets the same capability."** A server carrying CSA's
close-out procedure breaks that promise for everyone who is not CSA.

**It closes the capture loop.** The project's purpose is human + AI working tickets, captured as
skills, promoted to plugins, eventually run by an agent. The workflow plugin *is* the capture
artifact — which gives the enablement ladder's rung E2 a concrete deliverable instead of an
aspiration.

## What this costs, named rather than discovered later

**Partial failure becomes possible, and there is no transaction.** A human assigns, replies and
notes in one `PUT` — one API call, one audit entry, all or nothing. Three atomic tools mean three
round trips, three audit entries, and a state where the assign landed and the reply did not.

**The mitigation falls out of the reach axis: sequence irreversible actions last.** If
`reply_publicly` fails after `assign_ticket` succeeded, nothing has left the building and the retry
is free. If the order were reversed, a failed assign would leave a customer already emailed about a
ticket that is now misrouted. **Reach last** is guidance the example plugin should carry, and it is
the first piece of workflow advice this design produces on its own.

## Rejected alternatives

**Atomic tools plus one composite, gated by its arguments.** Technically available —
`policy.py`'s `Gate` accepts `Callable[[dict], frozenset[str]]` and was built for exactly this.
Rejected because an MCP annotation is static per tool, so a composite that *can* reply must be
annotated as reaching a person **always**, which is dishonest in the common case where it does not.
It also creates two ways to do one thing, which is `GOALS.md` failure mode #2 wearing a different
hat.

**One composite only, mirroring Zendesk exactly.** Fewest tools, always atomic, closest to the API.
Rejected on the authority argument above: no operator could grant field edits without also granting
the ability to email customers.

**Workflow guidance inside the server's instructions.** ADR-006's per-toolset instructions already
compose, so this would have been cheap. Rejected because it is tenant opinion shipped to every
tenant, and because the instructions are always-on context cost paid by deployments that do not
share the opinion.

## Affects

- `CLAUDE.md` architectural fact 6 — "`update_ticket` is deliberately broad" is now wrong and is corrected
- The whole-project design §4 — "group by task and argument shape" becomes "constrain the call"
- `analysis/operation-classification.csv` — cannot express call-level classification (TODO **B18**)
- The tool surface: more tools than operations in the ticket-write path, not fewer
- `policy.py`'s callable `Gate` may now have no user; do not remove it until the tool surface confirms that

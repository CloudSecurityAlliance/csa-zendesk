# ADR-004: Verify irreversible operations by observation, not by performing them

**Date:** 2026-08-31
**Status:** Active
**Decision method:** Collaborative — the distinction was the project owner's; the technique was
demonstrated and recorded jointly.

## Goal

Decide how to verify operations that cannot safely be exercised, without either shipping
untested code or excluding capabilities that matter.

## Context

[ADR-001](ADR-001.md) says we do not implement what we cannot test. That rule was written for
plan-gated families — permanently unreachable, so permanently unverifiable.

A second class exists, and it is different: operations that are **reachable but destructive**.
Closing a ticket is the worked example. It is permanent, the web interface does not offer it to
agents, and the only conventional test destroys a ticket — which this project has already done
once, accidentally, at the cost of a designated test ticket.

Treating that class the same as the plan-gated one would exclude legitimate capabilities. Testing
it conventionally means damaging real records on every test run.

## Decision

**Three testing tiers, not two.** The third is new:

| Tier | What it exercises | Against |
|---|---|---|
| **unit** | every code path | `FakeBackend`, offline, gates CI |
| **integration** | reads, and writes that can be undone | the live API, opt-in |
| **observational** | irreversible operations | **the platform's own instances of them, read-only** |

An operation qualifies for observational verification when **the platform performs it routinely
under its own rules**, leaving evidence we can read. We verify the behaviour by measuring what
the platform did, never by doing it ourselves.

For closure specifically, the observational test asserts:

- Closed tickets exist and are reached from solved.
- The elapsed time between the solve and the close clusters at the account's configured
  automation window, and those transitions are attributed to the `rule` channel.
- A closed ticket refuses subsequent writes — verifiable read-only, since the refusal is
  observable on any already-closed ticket.

**An operation with no observable instances and no safe test is excluded under ADR-001**, not
shipped untested. Account deletion is the reference case: nothing performs it routinely, there is
no second instance to observe, and it is out of scope regardless.

## Rationale

**The platform is already running the test suite.** For any lifecycle transition driven by
automation, production is a continuous, high-volume experiment whose results are queryable. Not
using that is choosing a worse signal.

**Observation reveals behaviour a write-test cannot.** The first run of this check found that
**half** the sampled closures came from the configured automation as expected — and that a
substantial fraction were forced within an hour through a web channel, despite the status picker
not offering Closed to agents. The likeliest explanation is **merging**, which closes the source
ticket. That is a second human-driven path to an irreversible state which no amount of testing
*our own* `close_ticket` call would ever have surfaced.

A write-test answers *did my call work?* Observation answers *how does this actually behave here,
including through paths I did not know about?* The second question is the one that produces
correct tool descriptions.

**It costs nothing and can run continuously.** Read-only, no fixtures, no cleanup, safe against
production. It can run in CI against a live account without the usual objection.

**It degrades honestly.** On an account where nothing has ever been closed, the check reports
*no evidence available* rather than passing vacuously. A test that cannot fail is theatre; this
one states when it has nothing to say.

## Rejected alternatives

**Test `close_ticket` conventionally against a disposable ticket.** Works exactly once per
ticket, and every CI run consumes one. It also verifies only the happy path of our own call,
telling us nothing about how closure happens in reality.

**Mark `close_ticket` untested and ship it anyway.** The position ADR-001 exists to prevent.

**Exclude `close_ticket` under ADR-001.** Over-broad: ADR-001's subject is what we *cannot reach*,
and closing is reachable. Applying it here would exclude a capability that is legitimately needed
for bulk lifecycle work, on a technicality about test mechanics.

**A sandbox account.** Right in principle and worth revisiting if one appears. It does not remove
the need for observation, because a sandbox has no production behaviour to observe — it would
verify our call and not the system.

## Implementation

- `tests/observational/` — opt-in, live, **read-only**, alongside the existing unit and
  integration tiers.
- The suite must report *insufficient evidence* distinctly from *pass*, and CI must not treat the
  two alike.
- Nothing it records may retain rows: distributions, counts and channel attributions only.
- `merge_tickets` is now understood to be a closing operation. Its capability gate and its tool
  description must say so — filed in `TODO.md`.

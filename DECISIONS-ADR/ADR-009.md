# ADR-009: Public OAuth client with PKCE, and exactly one token file

**Date:** 2026-09-08
**Status:** Active — token clause superseded by [ADR-015](ADR-015.md)
**Decision method:** AI proposal, human approved — the research is in `analysis/API-SURFACE.md` §7.

## Goal

Decide how the library authenticates, and resolve a contradiction: the design requires a token
store that three of this repository's own documents forbid.

## Context

Zendesk supports, for the Support API:

- **`authorization_code`** for **public clients**, where **PKCE (S256) is mandatory and no client
  secret is used**.
- **`client_credentials`** for confidential clients only.
- No password grant. No grant type is deprecated.

**API tokens die on 2027-04-30**, and no account can create one after 2026-10-27.

Two facts force the shape:

1. **A local stdio server cannot hold a secret.** So a confidential client is out, which rules out
   `client_credentials` regardless of its other merits.
2. **Access tokens are short-lived.** Clients created on or after 2026-04-30 get a 30-minute
   `expires_in` automatically; the permitted range is 5 minutes to 2 days. Refresh tokens exist but
   require an expiring access token.

Without persisting the refresh token, an operator re-authorises in a browser **every 30 minutes**.
That is not a usable product.

But `DECISIONS-ADR/ADR-005.md` and `CLAUDE.md` both say flatly *"no token file"*, and
`SECURITY.md` says *"no token file for `client_credentials`"* — three statements, two of which
forbid what the design needs, and one of which is correctly scoped.

## Decision

**A public OAuth client using `authorization_code` with PKCE (S256). No client secret anywhere.**

**Exactly one persisted artifact: a token file.** ADR-005's no-persistence position is amended to
read: **no response persistence, no attachment cache — and one token file, because refresh tokens
require it.** `CLAUDE.md` is corrected to match `SECURITY.md`'s scoping.

The token file:

- lives at `$XDG_CONFIG_HOME/csa-zendesk/tokens.json`, falling back to
  `~/.config/csa-zendesk/tokens.json`; overridable by `CSA_ZENDESK_TOKEN_FILE`
- is created mode **`0600`** inside a **`0700`** directory, and its mode is asserted on every read
- is written **atomically** (temp file, then rename) under a lock file, because refresh rotates the
  token and two MCP clients may run the server concurrently
- holds the refresh token, the access token and its expiry. **Nothing else. No ticket data.**

Refresh happens **before expiry** (within a small margin) and **on rejection**, retried once — but
only when Zendesk answers `401` with `invalid_token`. A `401` or `403` arising from scope or from
the operator's own Zendesk permissions is **passed through unchanged**, so a permissions problem
stays visible as a permissions problem rather than looking like auth flakiness.

~~**API token support ships, deprecated.** `CINO_CSA_ZENDESK` + `CINO_CSA_ZENDESK_EMAIL` continue to
work, log a deprecation warning once, and are overridden by OAuth when both are configured.~~

> **Superseded by [ADR-015](ADR-015.md) (2026-09-17).** There is no API token code path. The server
> authenticates by OAuth and by nothing else, and no further tokens are minted — the 2026-10-27
> window is allowed to close. The rest of this ADR stands. The research scripts under `scripts/` are
> exempt as development tooling.

**No client id is embedded.** The operator registers their own public client and supplies
`CSA_ZENDESK_CLIENT_ID`.

## Rationale

**The public-client path removes a problem the sibling project could not solve.** Google's terms
forbid embedding developer credentials in open source, which is why `csa-google-workspace`'s OAuth
client lives in a private repository. Zendesk's public clients use **no secret at all**, so a
client id is publishable and `csa-zendesk` can ship a complete auth story in a public repo with
nothing withheld.

**Per-operator identity is the reason to prefer this over `client_credentials`**, beyond the
secret problem. Tokens minted by `client_credentials` are attributed to whoever created the
client, so every operator's public replies and audit entries would name one administrator. Where a
human's name goes on outward-facing text (ADR-003), per-operator identity is the whole point.

**One token file is a smaller concession than it looks.** What it holds is a credential — which is
the category `SECURITY.md` already contemplates and protects — not customer data, which is the
category ADR-005 exists to keep off disk. Conflating the two produced the contradiction; separating
them resolves it without weakening either position.

**Retrying only on `invalid_token` is the non-obvious part.** Blanket-retrying `401`/`403` would
mask a scope misconfiguration as a transient fault, and scope errors here are common: Zendesk
issues a token for an unrecognised scope name and then refuses every request made with it, so a
typo produces a credential that looks valid and works for nothing.

## Rejected alternatives

**`client_credentials`.** Simpler — no browser, no refresh, no token file, and it would let
ADR-005 stand unamended. Rejected because it requires a confidential client, which a local server
cannot be, *and* because it collapses every operator into one identity.

**Embed a CSA-registered client id.** Convenient. Rejected as unnecessary: it makes every
deployment share one client's scope ceiling and rate-limit attribution, for no gain, since a
public client id is trivial for an operator to create.

**Keep tokens in memory only.** Honest to ADR-005 and unusable: re-authorisation every 30 minutes.

**Use the OS keychain instead of a file.** Better in principle. Rejected for 1.0 as a portability
and dependency cost disproportionate to a file the operator's own account can already read; worth
revisiting if this ever runs as a service.

## Implementation

- `auth.py` owns the flow, the store and refresh. A one-shot localhost listener handles the
  callback, with a paste-based fallback for remote shells.
- The token file's mode is **verified on read**, and a wrong mode is a loud error rather than a
  warning — a `0644` token file is a finding, not a preference.
- A test asserts the file is never written with anything other than the three token fields.
- Consistent with `SECURITY.md`: a credential never reaches a log line, an error message or a
  `__repr__`.

# ADR-003: Capability gates are drawn on reversibility, and public replies are their own tool

**Date:** 2026-08-31
**Status:** Active
**Decision method:** Collaborative — the ladder was proposed and refined jointly; the
internal/external split was the project owner's requirement.

## Goal

Decide how ticket-mutating authority is divided, given that a single `update_ticket` call can
carry consequences ranging from trivially reversible to permanent.

## Context

The web interface applies field edits, the comment and the status change in **one `PUT`**, and
[ADR-002](ADR-002.md)'s architecture mirrors that: one broad `update_ticket`. But those
consequences are not equivalent, and two of them cannot be undone:

- A **public comment emails the requester and every collaborator.** The mail has gone; deleting
  the comment afterwards does not recall it.
- **Solving is not itself terminal, but it is the on-ramp to terminal.** A tenant automation
  closes solved tickets after a fixed period — commonly two to four weeks — and a closed ticket
  refuses every subsequent write, including reopening (`API-SURFACE.md` §5.4d). Solving also
  removes the ticket from active views, which is precisely why nobody notices before the timer
  expires. It may fire a satisfaction survey and stop SLA clocks.
- **Closing is terminal immediately**, and the web UI does not even offer it.

Meanwhile an internal note never leaves the organisation, and a field edit is recorded in the
audit trail and can simply be edited back.

`comment.public` has **no fixed default** — it inherits from the ticket's first comment, so on
the common email-originated ticket it is *public* (`API-SURFACE.md` §5.4f).

## Decision

**Capabilities are ordered by whether the action can be undone**, following the line
`csa-google-workspace` draws for the same reason:

| Capability | Action | Reversible? | In the default profile |
|---|---|---|---|
| `ticket.read` | read tickets, comments, audits | n/a | yes |
| `ticket.note` | add an **internal** note | yes — never leaves the org | yes |
| `ticket.write` | fields, assignee, tags, priority, form | yes — audited | yes |
| `ticket.reply` | add a **public** comment | **no** — the email has gone | **no** |
| `ticket.solve` | set status to solved | for a period, then no | **no** |
| `ticket.close` | set status to closed | **no**, immediately | **no** |

**A public reply is a separate tool, not a parameter.**

- `update_ticket` — fields, status, and optionally a comment that is **always internal**. It
  cannot produce a public comment at all.
- `add_public_reply` — the **only** path to a public comment.
- `close_ticket` — the only path to `closed`.

**`public` is never omitted anywhere in the codebase.** The backend sends it explicitly on every
comment write.

## Rationale

**Tool annotations are per-tool, and these actions have different risk profiles.** This is the
argument that settles it. MCP annotations (`destructive_hint`, `read_only_hint`) attach to a
tool, not to an invocation. If one tool can both edit a field and email a customer, it must be
annotated for the worst case — so every routine field edit is advertised as destructive, and a
client that sees `destructive_hint: true` on the tool it uses constantly learns to ignore the
hint. Separating them lets each annotation be **true**, which is the only way an annotation is
worth anything.

**A wrong tool name is a rarer mistake than a wrong boolean.** The failure we are guarding
against is *intended an internal note, produced a public reply*. With one tool that is a flipped
flag one token wide. With two tools it requires selecting a differently-named tool whose name
says what it does. Models mis-set booleans considerably more often than they call the wrong
obviously-named tool.

**Zendesk's own interface draws this line visually.** The agent composer changes its background
colour between public reply and internal note, because the vendor concluded a toggle alone was
too quiet for a decision this consequential. A distinct tool name is the API equivalent of that
colour change.

**Splitting also improves the failure mode.** "Solve with a public reply" becomes two calls
rather than one atomic `PUT`. That looks like a loss, but consider the atomic version failing
required-field validation on solve: the reply is discarded along with it, and the agent believes
they have replied. Split, the reply lands and only the solve is refused — a recoverable state
that is visible to a human.

**The gate is computed from the arguments.** `update_ticket` still needs `ticket.write` for a
field change and `ticket.solve` when `status == "solved"`, in one call. So a `_GATES` entry may
be a **function of the call's kwargs returning a set of required capabilities**, rather than a
constant. The table remains the single declaration point, it still fails closed on an undeclared
method, and enforcement still lives in the wrapper around the seam rather than in the tools — so
[ADR-002](ADR-002.md)'s uniformity property is preserved. All required capabilities are checked
before anything is written.

## Rejected alternatives

**One `update_ticket` with a required `public` parameter.** Simpler, and it matches the UI's
single submit exactly. Rejected on the annotation argument above: one tool cannot carry two
honest annotations. Making `public` required removes the *inheritance* hazard but not the
flipped-boolean one.

**Gate on the payload inside the tool.** Would work, and is what most servers would do. Rejected
because it moves enforcement into the delivery layer, so a library embedder calling the backend
directly gets no protection — the exact property the wrapper exists to guarantee.

**Split the backend into `update_fields` / `add_comment` / `set_status`.** Three methods, three
constant gates, no argument-dependent logic. Rejected because it means three `PUT`s where the UI
does one, and a half-applied update is worse than a refused one.

**Put `ticket.reply` in the default profile.** Rejected: the default must be the set of things
that can be undone. An install that has not thought about it should not be able to email a
customer.

**Omit `close_ticket` from v1.** Seriously considered, since the web UI does not expose Closed.
Decided to build it *and grant it in no profile*, so the capability exists to be enabled
deliberately rather than being an absence someone works around with a raw API call.

## Implementation

Not yet built. When it is:

- `_GATES` supports a callable returning `frozenset[str]`, and `tests/` asserts every `Backend`
  method still has an entry — the fail-closed property must survive the change.
- Annotations: `update_ticket` is `destructive_hint: false`; `add_public_reply` and
  `close_ticket` are `destructive_hint: true`.
- `add_public_reply`'s description states that it emails the requester and all collaborators and
  cannot be recalled. `close_ticket`'s states that closing is permanent and that solved is
  probably what was meant.
- Prompt-injection wrapping matters most on this path: ticket content is untrusted, and
  `add_public_reply` is the tool that sends text back out of the organisation.
